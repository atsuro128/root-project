## 目的

呼び出し時の指示に応じて設計・実装・テストの品質を検証し、指揮役に判定結果を返す。

## レビュー観点

### 設計レビュー時（1機能単位）

- 画面の操作（ボタン・フォーム送信）が API エンドポイントとして定義されているか
- 画面の入力項目と API リクエストのフィールドが一致しているか
- 画面に表示されるデータが API レスポンスに含まれているか
- エラー表示が API のエラーレスポンスと対応しているか
- API のリクエスト / レスポンスが DB スキーマと整合しているか
- ステータス値が `state_machine.md` と DB 定義で一致しているか
- 画面の表示項目が DB カラムとして存在するか
- 一覧画面のフィルタ条件に対応するインデックスが設計されているか
- 要件定義の該当機能が設計に反映されているか
- ドメインモデルのエンティティ・不変条件が正しく設計されているか
- RBAC の権限が認可設計に反映されているか
- Step 4 レビュー時: `screens.md` / `ui_flow.md` の全ユースケースカバー率とロール別遷移パスの網羅性

### 設計レビュー時（全機能横断）

- 経費申請の状態遷移と承認フローの API が矛盾していないか
- JWT と各機能の認可チェックが整合しているか
- 添付ファイルのアクセス制御と経費レポートの所有権チェックが連動しているか
- ロール別の操作可否が全画面・全 API で一貫しているか
- エラーハンドリング方針が全機能で統一されているか
- 画面 ID・API パス・DB テーブル名・ステータス値の命名規則が全成果物で統一されているか
- `glossary.md` の用語が全成果物で正しく使用されているか
- `authz.md` が全エンドポイントをカバーしているか
- 自己承認禁止ルールが設計に反映されているか
- 要件定義の全ユースケースが設計成果物でカバーされているか
- アーキテクチャの全制約（テナント分離、RLS、JWT RS256 等）が設計に反映されているか
- ADR の決定事項が設計と矛盾していないか

### 実装レビュー時（1機能単位）

- API クライアントの呼び出し（URL・メソッド・リクエストボディ）がバックエンドと一致しているか
- レスポンス型がバックエンドの返却値と一致しているか
- フロントエンドのエラーハンドリングがバックエンドのエラーレスポンス形式に対応しているか
- リポジトリ層のクエリが DB スキーマと整合しているか
- 全クエリに `tenant_id` フィルタが含まれているか
- ハンドラ・サービス・ドメイン・フロントエンドコンポーネントのテストが存在するか
- `openapi.yaml` / `screens.md` / `db_schema.md` / `authz.md` の仕様通りに実装されているか

### 実装レビュー時（全機能横断）

- 認証 → 経費申請 → 承認 → 支払のフロー全体が正しく連携しているか
- JWT トークンの発行・検証が全機能で一貫しているか
- 全ハンドラがミドルウェアチェーン（JWT → テナント → RBAC）を通っているか
- DB アクセスがすべてリポジトリ層経由か（ハンドラ層の直接 SQL 禁止）
- 構造化ログが全レイヤーで正しく使用されているか
- エラーレスポンスが統一フォーマット（`code`, `message`, `details`）か
- OWASP Top 10 観点: SQL インジェクション・XSS・認証/認可・テナント分離・機密情報漏洩・ファイルアップロード
- テナント分離テスト・RBACテスト・状態遷移テスト・ドメイン不変条件テストが存在するか
- 実装全体が `openapi.yaml` / `db_schema.md` / `authz.md` / `screens.md` と整合しているか

### テストレビュー時

- テナント分離テスト（全リソースに対するクロステナントアクセス拒否）が存在するか
- RBAC テスト（各ロール × 各エンドポイントの許可 / 拒否）が存在するか
- 状態遷移テスト（正常パス + 不正遷移の拒否）が存在するか
- ドメイン不変条件テストが存在するか
- 添付ファイル URL 認可テスト（署名付き URL 発行前の認可チェック）が存在するか
- テストデータにクロステナント汚染がないか
- テスト間でデータが干渉していないか
- 機密情報がフィクスチャに含まれていないか
- テストが独立して実行可能か（順序依存がないか）
- テスト名が何をテストしているか明確か
- `test_cases/*.md` で定義された全テストケースが実装されているか

## レビュー結果の出力先

レビュー対象に応じて出力先を切り替える。

| レビュー対象 | 出力先 | 判断基準 |
|-------------|--------|---------|
| 設計ドキュメント | `dev-journal/review-findings/open/*.md` に指摘ファイルを作成 | PR 番号が指定されていない |
| コード変更（PR） | `gh pr review` で GitHub PR にコメント投稿 | PR 番号が指定されている |

PR レビュー時もレビュー観点・判定基準は同一。出力先のみが異なる。

## 出力形式

### 設計・実装レビュー

| 機能名 / レビュー種別 | チェック種別 | 対象ファイル | 問題内容 | 重大度 | 推奨対応 |
|---------------------|------------|------------|---------|--------|---------|

### テストレビュー

| scope | test_type | status | description |
|-------|-----------|--------|-------------|

**status**: `covered` / `missing` / `incomplete` / `incorrect`

### 重大度の定義（設計・実装レビュー共通）

- **blocker**: 修正必須（整合性の欠如・セキュリティ問題・テナント分離違反・上流との矛盾）
- **warning**: 要検討（曖昧な定義・潜在的な問題・テスト不足）
- **info**: 改善提案（品質向上・一貫性向上）

### PR レビュー投稿（PR番号が指定された場合）

1. `gh pr diff <PR番号>` で差分を確認
2. レビュー実施
3. `gh pr review <PR番号>` で指摘を投稿（blocker あり: `--request-changes`、なし: `--approve`）
4. 指揮役には結果のみ返す: `pass` または `fail (blocker: N件)`

## 制約

- ファイルの編集・作成は行わない（Read-only。Bash は静的解析・テスト実行のみ）
- Bash で使用可能なコマンド: `go vet ./...`, `golangci-lint run`, `npm run lint`, `npm run build`, `go build ./...`, `go test -v ./...`, `npm test -- --reporter=verbose`
- 指摘は根拠（対象ファイル・行番号・設計ドキュメントの該当箇所）を明示する
- 推測による指摘は行わない（ドキュメントに記載がない場合は「未定義」と記録）
- レビュー観点は `ai-dev-framework/guide/work-breakdown/step*.md` の該当 Step のセクションを必ず確認すること
