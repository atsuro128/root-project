開発プロセスの分析資料を作成してください。

## 現在の日時

!`date "+%Y-%m-%d %H:%M"`

## 引数

$ARGUMENTS

（引数がない場合は、期間をユーザーに確認すること）

## モード判定

引数から以下のどちらかを判定する:

| モード | 条件 | 出力先 | 出力形式 |
|--------|------|--------|---------|
| **週次レビュー** | テーマ指定なし（期間のみ） | `dev-journal/archives/weekly-reports/review-YYYY-MM-DD-to-DD.md` | 固定構成（下記） |
| **テーマ分析** | テーマ指定あり | ユーザーに確認 | ユーザーに確認 |

## 手順

### Phase 1: パラメータ確定

引数から期間を特定する。相対表現（「直近1週間」「先週」等）は絶対日付に変換する。

**テーマ分析モードの場合のみ**、以下をユーザーに確認する:
- **出力フォーマット**: 時系列ナラティブ / Before-After 比較表 / 両方の組み合わせ
- **想定読者**: ポートフォリオ向け / 自分用振り返り / ブログ記事・発信用
- **出力先ディレクトリ**
- **言語**: 日本語 / 英語

### Phase 2: ソース収集

以下のソースを **Agent ツールで並列に** 収集する。日数が4日以上の場合はセッションログと日報を別エージェントに分ける。

| ソース | パス | 用途 |
|--------|------|------|
| セッションログ | `dev-journal/progress-management/session-log.md`, `dev-journal/archives/session-logs/YYYY-MM-DD.md` | セッション単位の作業ログ・判断・学び |
| 日報 | `dev-journal/archives/daily-reports/YYYY-MM-DD.md` | 日ごとの成果サマリー |
| ADR | `dev-journal/references/decisions/ADR-*.md` | 期間内に作成・変更されたもの |
| 進捗管理 | `dev-journal/progress-management/progress.md` | Step 進行状況 |
| Git 履歴 | `git log --since=START --until=END+1 --oneline --format="%h %ad %s" --date=short` | コミット単位の変更履歴 |

- 期間内のファイルのみを対象とする

### Phase 3: 分析・構造化

収集した情報を整理する:

1. **時系列の整理**: 何がいつ起きたかを日付順に並べる
2. **因果関係の抽出**: 「何が起きた → なぜ変えた → どう良くなった」の流れを特定する
3. **パターンの発見**: 繰り返し現れるテーマや傾向を見つける
4. **Before/After の特定**: 主要な観点での変化を対比可能な形にまとめる

### Phase 4: 執筆

#### 週次レビューモード

以下の固定構成で執筆する:

```markdown
# 総評: YYYY-MM-DD 〜 YYYY-MM-DD

## 概要
（3行以内で期間全体を要約）

---

## 1. プロダクト進捗
（Step の進行、expense-saas のコード量、ブロッカー。表形式を活用）

## 2. 基盤・ツーリング整備
（分野ごとに小見出しをつけ、事実 + 所感。時間の使い方を率直に評価）

## 3. 意思決定の質
（良かった点 / 気になった点に分けて箇条書き）

## 4. 気になるパターン
（パターン名 + 具体例 + 示唆。2〜4個程度）

## 5. 数値サマリー
（表形式で主要指標を列挙）

## 6. 次週への示唆
（3〜5項目。具体的なアクションを含む）
```

#### テーマ分析モード

想定読者とフォーマットに応じて資料を執筆する。

- **ポートフォリオ向け**: 技術的判断の「なぜ」を重視。試行錯誤のプロセスを正直に記述
- **自分用振り返り**: 事実ベースで簡潔に。次に活かせるアクションを明確に
- **ブログ記事・発信用**: 読者の前提知識を想定し、背景説明と具体例を加える

### 共通の執筆ルール

- 事実ベースで書く。推測には「〜かもしれない」「要確認」を付ける
- 良い点と懸念を両方書く。懸念は具体的な改善案とセットにする
- 「明日以降のタスク」が複数日にわたり繰り越されていたら、その事実を明記する

### Phase 5: 検証

- 日付・コミットハッシュ・Issue 番号がソースと一致することを確認する
- 作成した資料をユーザーに提示し、修正点を確認する
