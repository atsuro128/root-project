開発プロセスの分析資料を作成してください。

## 現在の日時

!`date "+%Y-%m-%d %H:%M"`

## 引数

$ARGUMENTS

（引数がない場合は、期間と分析テーマをユーザーに確認すること）

## 手順

### Phase 1: パラメータ確定

引数から期間と分析テーマを特定する。不足があればユーザーに確認する。

さらに以下をユーザーに確認する:
- **出力フォーマット**: 時系列ナラティブ / Before-After 比較表 / 両方の組み合わせ
- **想定読者**: ポートフォリオ向け / 自分用振り返り / ブログ記事・発信用
- **出力先ディレクトリ**
- **言語**: 日本語 / 英語

### Phase 2: ソース収集

指定期間内の以下のソースを並列で読み込む:

| ソース | パス | 用途 |
|--------|------|------|
| セッションログ | `dev-journal/progress-management/session-log.md`, `dev-journal/logs/session-log-archive.md` | セッション単位の作業ログ・判断・学び |
| 日報 | `dev-journal/daily-reports/YYYY-MM-DD.md` | 日ごとの成果サマリー |
| ADR | `dev-journal/references/decisions/ADR-*.md` | 構造的判断の根拠 |
| 進捗管理 | `dev-journal/progress-management/progress.md` | Step 進行状況 |
| Git 履歴 | `git log --since=START --until=END --oneline` | コミット単位の変更履歴 |

- 期間内のファイルのみを対象とする
- Agent ツールを活用し、日数が多い場合は複数エージェントで並列読み込みする

### Phase 3: 分析・構造化

収集した情報を分析テーマの観点で整理する:

1. **時系列の整理**: 何がいつ起きたかを日付順に並べる
2. **因果関係の抽出**: 「何が起きた → なぜ変えた → どう良くなった」の流れを特定する
3. **パターンの発見**: 繰り返し現れるテーマや傾向を見つける
4. **Before/After の特定**: 主要な観点での変化を対比可能な形にまとめる

### Phase 4: 執筆

想定読者とフォーマットに応じて資料を執筆する。

#### ポートフォリオ向けの場合
- 技術的判断の「なぜ」を重視する
- 試行錯誤のプロセスを正直に記述する（失敗→学び→改善）
- 得られた知見を汎用的な形でまとめる

#### 自分用振り返りの場合
- 事実ベースで簡潔にまとめる
- 次に活かせるアクションを明確にする

#### ブログ記事・発信用の場合
- 読者の前提知識を想定し、必要な背景説明を加える
- 具体例を交えて読みやすくする

### Phase 5: 検証

- 日付・事実がソースと矛盾しないことを確認する
- 各セクションが分析テーマに沿っていることを確認する
- 作成した資料をユーザーに提示し、修正点を確認する
