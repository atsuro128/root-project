指定された機能・テーマについて要件定義を行い、成果物を作成してください。

対象: $ARGUMENTS
（引数がない場合は、dev-journal/progress-management/progress.md の直近タスクから対象を判断する）

## 前提の確認
1. dev-journal/deliverables/docs/02_scope.md を読み、対象機能が MVP スコープ内か確認する
2. dev-journal/references/glossary.md を読み、用語を統一する
3. 既存の要件定義成果物（dev-journal/deliverables/docs/10_requirements/）があれば読み、整合性を保つ
4. 他機能との依存関係・連携ポイントを把握する

## 要件整理の観点
以下の観点で漏れなく整理すること：

### 機能要件
- **アクター**: 誰がこの機能を使うか（Admin / Approver / Member / Accounting）
- **ユースケース**: 正常系・代替系・例外系を網羅
- **入力/出力**: 各操作の入力データと期待される出力
- **ビジネスルール**: 制約条件・バリデーション・不変条件
- **状態遷移**: 状態を持つ場合、遷移図（Mermaid）と禁止操作を定義

### 非機能要件
- **パフォーマンス**: レスポンスタイム、スループットの期待値
- **セキュリティ**: 認証・認可・テナント分離の要件
- **データ**: 保持期間、サイズ制限、整合性
- **ユーザビリティ**: 操作性・アクセシビリティの考慮（該当する場合）

### スコープ判定
- MVP で実装する範囲と Phase 3 以降に回す範囲を明記
- 「やらないこと」とその理由を明記
- 将来の拡張性に影響する設計判断があれば明記
- 既存データの移行・互換性の考慮が必要な場合は記載

### 追加レビュー観点（整合性・品質）
- **仕様間整合性**: requirements/usecases/workflow/rbac で役割・操作・状態遷移が矛盾していないか
- **トレーサビリティ**: ルールIDを参照している箇所に、定義元が必ず存在し追跡可能か
- **検証可能性**: 各要件がテストケースに落とせる具体度（入力条件・期待結果・エラー条件）になっているか
- **曖昧性排除**: 「必要に応じて」「適切に」など実装解釈が分かれる表現を避け、判断基準を明記しているか
- **意思決定の確定状態**: 「検討中」「判断が必要」の項目が残っていないか（残す場合は決定予定日と責任者を明記）

## 出力形式
- 成果物は dev-journal/deliverables/docs/10_requirements/ に配置
- 状態遷移がある場合は Mermaid 記法で図を含める
- RBAC に関わる場合はロール×操作の権限マトリクスを含める

## 品質チェック
作成後、以下を自己チェック：
- [ ] 用語が dev-journal/references/glossary.md と一致しているか
- [ ] MVP スコープを逸脱していないか
- [ ] 「誰が」「何を」「どの順で」が説明できるか
- [ ] 例外ケース（却下・エラー・権限不足）を網羅しているか
- [ ] CLAUDE.md のアーキテクチャ制約（tenant_id 必須、ドメイン層での状態遷移管理等）と矛盾していないか
- [ ] 主要ドキュメント間（requirements/usecases/workflow/rbac）で権限・状態・操作が一致しているか
- [ ] 参照したルールID（SEC/RBC/WFL等）に未定義がないか
- [ ] 要件がテスト可能な粒度（前提・入力・期待結果・異常系）で書かれているか
