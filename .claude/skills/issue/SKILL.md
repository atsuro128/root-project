Issue 管理ルールに従って操作を実行してください。

対象: $ARGUMENTS

## 操作の判定

引数から操作を判定する:
- `起票` / `create` / `new` → 起票フロー
- `対応` / `handle` / `resolve` / `fix` → 対応フロー
- `一覧` / `list` / `確認` → 一覧・確認フロー
- 引数なし / 曖昧 → ユーザーに操作種別を確認

## 共通情報

### フォルダ構成

```
dev-journal/issues/
├── open/             # 未対応・対応中の issue
├── pending-review/   # 解決内容を記入済み・レビュー待ち
└── resolved/         # レビュー完了・クローズ済み
```

### ファイル命名規則

- プロダクト系: `NNN-kebab-case.md`
- 運用系: `ops-NNN-kebab-case.md`

番号は3桁ゼロ埋めのグローバル連番（プロダクト系・運用系で共通、3フォルダ横断で一意）。
カテゴリが `project-management` または `ai-ops` の場合は運用系（`ops-` プレフィクス）とする。

### カテゴリ一覧

| カテゴリ | 対象 |
|---------|------|
| `requirements` | 要件定義・仕様の問題 |
| `domain` | ドメインロジック・ビジネスルールの問題 |
| `architecture` | アーキテクチャ・設計構造の問題 |
| `ui-design` | UI/UX 設計の問題 |
| `detail-design` | 詳細設計（API・DB・インターフェース）の問題 |
| `testing` | テスト戦略・テストコードの問題 |
| `implementation` | 実装・コードの問題 |
| `security` | セキュリティ上の問題 |
| `infrastructure` | インフラ・CI/CD・環境の問題 |
| `project-management` | プロジェクト管理・運用ルールの問題 |
| `ai-ops` | AI（Claude Code）の運用・操作ミス・改善 |

### 影響度の基準

| 影響度 | 基準 |
|-------|------|
| `高` | 放置すると設計判断・実装に直接支障をきたす |
| `中` | 次フェーズまでに対処が必要 |
| `低` | 改善提案・優先度低 |

### 発見経緯の分類

| 値 | 意味 | 典型的な状況 |
|----|------|-------------|
| `proactive` | 成果物作成中に Claude が能動的に発見 | 設計中に矛盾・曖昧さに気づいた |
| `review` | codex-review / ユーザーレビューで発見 | レビュー工程での指摘 |
| `escalation` | review-findings から issue に昇格 | 指摘対応中にスコープが大きいと判明 |
| `user-report` | ユーザーが直接報告 | ユーザーが問題を発見・報告 |

## 起票フロー

1. **起票**: `issues/open/[ops-]NNN-kebab-case.md` を作成（テンプレート: `ai-dev-framework/templates/issue-template.md`）
2. **正当性検証**（外部起票・レビュー指摘から昇格した issue の場合）
   - 当該ステップの関連資料を確認する
   - 上流の成果物も確認する
   - issue の妥当性を判断し、検証結果をユーザーに報告する
   - **対応不要の場合**: issue ファイルに判断理由を記載 → ユーザー確認後 `pending-review/` へ移動

### 成果物作成中の即時起票

Issue 発掘規約（`ai-dev-framework/guide/workflow.md`）の即時起票条件を満たす場合:

1. **中断**: 現在の作業を中断し、発見した問題をユーザーに報告する
2. **判断**: ユーザーの判断を仰ぐ（起票する / 懸念として記録 / 対応不要）
3. **起票**: ユーザーが起票を承認した場合、テンプレートの「発見経緯」に `proactive` を設定して起票
4. **再開**: 元の作業を再開する

## 対応フロー

1. **issue 読み込み**: `issues/open/` 配下の対象 issue を Read し、要件・受け入れ条件・発見経緯・追加対応ログ（ある場合）を把握する
2. **上流資料確認**: 関連する設計書・要件定義・テストケース等を、要件 ID・テストケース ID で全文検索して参照する（memory `feedback_issue_upstream_check`）
3. **方針提案**: 原因・修正範囲・影響範囲・代替案をユーザーに提案し、合意を得る
4. **実装着手**（方針合意後）:
   - 実装・テストが必要 → `/implement` スキルで実装エージェント起動（issue ID を引数で指定）
   - 設計書修正のみ → designer エージェント起動
   - dev-journal 内の軽微修正 → 指揮役が直接編集
5. **対応完了後**:
   - issue ファイルに解決内容・解決日を追記
   - **【必須】ユーザーに確認**（確認なしに `pending-review/` / `resolved/` へ移動してはならない）
   - レビューが必要 → `pending-review/` へ移動
   - 重要度が低くレビュー不要 → `resolved/` へ直接移動
6. **レビュー後**（pending-review 経由の場合）: `resolved/` へ移動

## 一覧・確認フロー

1. **一覧表示**: `dev-journal/issues/open/` を Glob して未対応 issue のファイル名を列挙する
2. **内容確認**: 特定 issue が指定されていれば Read して概要（タイトル・影響度・発見経緯・ブロッカー有無）を報告する
3. **優先度の判断**: 影響度・発見経緯から対応優先度を提案し、ユーザーの着手判断を仰ぐ
